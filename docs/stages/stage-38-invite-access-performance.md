# 阶段 38：邀请码访问与加载优化

## 目标

使用单一邀请码访问整个模况站点，不要求邮箱或账号；同时移除平台私有访问层对每个静态资源的重复验证，并降低已授权读者重复打开公开情报页的等待时间。

## 邀请访问

- `/invite` 提供邀请码输入页，成功后写入 HttpOnly、Secure、SameSite=Lax 的签名访问 Cookie。
- 访问状态有效期为 7 天，签名使用托管 Secret，浏览器无法伪造角色或延长有效期。
- 邀请码只在兑换时查询 D1，数据库仅保存 SHA-256 摘要，不保存明文。
- Alpha 批次包含 20 个普通邀请码和 1 个管理员邀请码；普通邀请码最多兑换 3 次，管理员邀请码最多兑换 10 次。
- 普通邀请码不能访问审核后台；管理员邀请码可继续使用运行监控和后台能力。
- QStash 自动化继续通过原有 Bearer Token 调用后台，不依赖浏览器邀请码。

## 加载优化

- Sites 访问范围改为公开后，静态 CSS、JavaScript 和图标不再逐个经过平台用户验证。
- 网站正文仍在 Worker 入口先验证签名访问 Cookie，未授权页面统一跳转邀请码页。
- 首页、事件详情、主题页和事件 API 在验证通过后使用 60 秒边缘缓存。
- 缓存不包含后台、邀请码兑换、订阅写入和其他用户写操作。

## 安全边界

- 生产必须设置 `INVITE_ACCESS_MODE=enforced` 和至少 32 字节的 `INVITE_SESSION_SECRET`。
- Worker 会删除客户端伪造的内部角色请求头，只接受签名 Cookie 解出的角色。
- 邀请模式下向搜索引擎返回 `noindex, nofollow`，并通过 robots 禁止抓取。
- 邀请码明文只保存在被 Git 忽略的 `.invite-codes.local.txt`，不会进入仓库或部署包。
