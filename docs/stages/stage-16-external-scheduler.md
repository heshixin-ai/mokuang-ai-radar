# Stage 16：外部定时刷新

## 目标

在 Sites 当前没有执行 Worker scheduled handler 的情况下，保留现有私有站点和 D1 数据库，通过受保护的 HTTP 入口接入支持 Timer 的外部调度器。

## 已完成

- 新增 `POST /api/v1/admin/refresh`，继续使用审核自动化 Bearer Token 鉴权。
- 请求方不能传入来源 URL、来源 ID、并发数或分析数量，所有工作量由服务端配置限制。
- 单次默认最多处理 4 个到期来源、并发 2 个抓取任务和 1 条 AI 分析。
- 每个来源继续写入 `trigger_kind=scheduled` 的运行记录，并把实际自动化身份写入 `triggered_by`。
- 同一来源并发运行继续由 D1 原子领取阻止；重复请求不会并行抓取同一来源。
- 每次刷新结束后运行幂等日报检查；未到发送时间或当日已经领取时不会重复发送。
- 新增通用命令行调用器和私有 GitHub Actions 定时工作流。

## 验证结果

- 本地真实小批量刷新：4 个来源全部成功，发现 40 条、新增 13 条、重复 27 条；完成 1 条 AI 分析，总耗时约 7.2 秒。
- 自动化测试 38 项通过、1 项跳过；Lint 和生产构建通过。
- Sites 版本 8 已发布，新入口已包含在生产构建中。
- GitHub Actions 手动运行成功：4 个来源全部成功、新增 40 条、完成 1 条 AI 分析并创建 1 条候选，总耗时约 10 秒；生产 D1 同步出现 4 条 `trigger_kind=scheduled` 且 `triggered_by=automation@mokuang.internal` 的成功记录。

## 外部调度配置

- 运行平台：私有 GitHub 仓库中的 GitHub Actions。
- 运行频率：`4-59/5 * * * *`，即避开 GitHub Actions 常见整 5 分钟队列后仍保持每 5 分钟运行；同时保留手动触发入口用于上线验收。
- 工作流使用固定并发组，不取消正在执行的刷新，单次超时 2 分钟。
- 仓库 Actions 只保存三个 Secret：生产站点 URL、审核自动化 Token、Sites 私有访问绕过 Token。
- 工作流日志只输出计数和耗时，不输出 URL、新闻标题、正文或 Token。

## 平台验证记录

曾部署 veFaaS 北京区域 Runtime Function 做连通性验证，但其出口请求被生产站点的 Cloudflare 防护返回 403，因此没有启用 Timer。最终改用私有 GitHub Actions，手动工作流与生产 D1 已通过验收。

GitHub 工作流已处于 active，文件位于默认分支，并把触发分钟错开到每小时 04、09、14…59 分。上线观察期间仍未产生首条 `schedule` 事件；GitHub 官方说明计划事件在高负载时可能延迟，负载足够高时甚至可能丢弃。因此当前状态是“自动调度已配置、手动生产链路已验证、平台首次定时投递待持续观察”，不能把手动运行冒充为定时验收。
