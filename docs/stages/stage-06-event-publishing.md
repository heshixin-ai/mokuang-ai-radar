# 第 6 阶段技术开发文档｜正式事件与发布门禁

> 配套文档：`mokuang-prd.html`、《AI 产品 Vibe Coding 通用技术栈手册》与《技术适配声明》。本文档只覆盖第 6 阶段。

## 一、阶段结论

- 已批准候选可以继续生成正式事件草稿，补齐中文标题、短说明、影响角色、为什么重要、建议行动和字段级引用。
- 草稿生成采用 P-03 影响分析与 P-04 中文情报稿两个独立阶段；事实基线来自已经人工批准的候选，后续阶段不得修改已确认事实。
- 正式草稿不等于发布。确定性质量门禁与人工发布是两个独立步骤；定时任务、候选批准和草稿生成均不会自动进入公开信息流。
- 公开事件仓库只查询 `published` 状态；当前本地 3 条正式事件都保持为草稿，因此公开页仍展示版本化演示数据。

## 二、正式事件数据模型

新增四张 D1 表：

| 表 | 作用 |
| --- | --- |
| `events` | 正式事件内容、草稿/发布/撤下状态、质量门禁、模型版本和生成成本 |
| `event_sources` | 事件与原始文档的多对多关系，并标记主来源 |
| `event_citations` | 最小事实主张、对应文档和支持字段 |
| `publication_actions` | 草稿创建、发布、撤下的操作者、备注与事件快照 |

常用查询使用 `status + updated_at`、`published_at`、事件与文档关系索引；迁移结尾执行 `PRAGMA optimize`。

## 三、草稿生成链路

```text
approved candidate
  → P-03 影响分析与行动建议
  → P-04 中文情报稿与 claims
  → source_id 白名单校验
  → 确定性质量门禁
  → draft
```

- 只有 `review_status=approved` 的候选可以生成草稿。
- 同一候选只生成一个正式事件；重复请求直接返回已有草稿，不重复调用模型。
- P-03 分别判断 product、developer、founder、researcher 的影响，建议必须是行动而不是事实。
- P-04 只能重组已批准事实与 P-03 影响判断；claims 只能引用输入文档 ID。
- `deck_zh` 最终由服务端按 50 个字符安全截断，避免供应商对 JSON Schema 长度约束执行不稳定导致整个草稿丢失。
- 高能力模型暂时不可用时回退到已评测的主模型；回退结果仍必须通过同一质量门禁。

## 四、发布质量门禁

以下任一条件会阻断发布：

- P-03 返回证据不足；
- 没有任何受影响角色；
- 没有字段引用；
- 综合置信度低于 0.8；
- P-03 或 P-04 主动要求再次人工复核；
- 只有社区线索级证据；
- 价格、政策、融资等高风险候选缺少人工审核说明。

门禁通过也不会自动发布。审核员必须在 `/review` 的“正式事件与发布门禁”区域单独点击发布；撤下必须填写原因。

## 五、接口与权限

- `POST /api/v1/admin/candidates/:id/draft`：为已批准候选生成或读取幂等正式草稿。
- `GET /api/v1/admin/events`：读取草稿、门禁、已发布与已撤下状态。
- `POST /api/v1/admin/events/:id/publication`：执行 `publish | withdraw`；发布必须通过门禁，撤下必须填写原因。
- 所有写接口继续使用服务端审核身份与邮箱白名单；公开 API 不接受内部状态参数，也不返回草稿。

## 六、真实链路验证

本地保留原有候选与审核数据后应用 `0002_deep_dagger.sql`。全部 3 条已批准候选均通过真实 DeepSeek 草稿链路：

| 草稿 | 结果 | 说明 |
| --- | --- | --- |
| vLLM v0.28.0 构建变更 | ready | 官方单一来源、引用完整、综合置信度 0.8 |
| GPT-5.6 ARC-AGI-3 API 设置 | ready | 官方单一来源、2 条 claims、综合置信度 0.8 |
| ChatGPT Academic Researchers 免费计划 | blocked | P-03 与 P-04 均要求再次复核权益范围与资格门槛 |

额外验证：

- 对已生成草稿重复请求不会再次调用模型。
- 尝试发布 blocked 草稿返回 `409 PUBLICATION_GATE_BLOCKED`，状态仍为草稿。
- `publication_actions` 当前只有 3 条 `draft_created`；没有 `published` 或 `withdrawn`。
- 公开事件 API 的 `meta.demo=true`，证明没有内部草稿泄漏到公开信息流。

## 七、测试要求

- `npm test`：领域、Prompt、草稿生成、质量门禁、采集与调度回归。
- `npm run lint`：代码规范。
- `npm run build`：Cloudflare Worker 兼容构建。
- `node --test tests/rendered-html.test.mjs`：首页、详情、公开 API 与受保护后台的构建后渲染。
- `npm audit --omit=dev`：生产依赖审计。

## 八、剩余风险与下一阶段

- 当前一个候选对应一个正式事件，还没有把不同文档的同一事件合并到同一事件记录；下一阶段应接入 recent existing events 与人工合并建议。
- 草稿只能重新生成，尚无字段级人工编辑和修订对比；发布前编辑与修订历史需要单独实现。
- P-03/P-04 的质量门槛只有真实样本基线，尚未达到 PRD 的 120 条黄金集规模。
- 实体时间线、主题页和每日邮件仍未接入。
