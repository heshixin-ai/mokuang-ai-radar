# 技术适配声明

## 1. 产品形态判断

- 产品类型与核心任务：面向中文 AI 产品经理、开发者和小型创业团队的 AI 变化情报产品；把多个来源的更新整理为可核验、可行动的事件。
- 核心交互：固定流水线处理 + 人工审核 + 信息流浏览；不是开放式动态 Agent。
- 开发路径：纵向切片。AI 事件质量需要结合来源在界面中人工判断，第一阶段同时实现最小核心服务和最小验收界面。
- 当前阶段范围：跑通“样例来源 → 抽取候选 → 合并判断 → 事件详情与引用”的核心链路。

## 2. 采用的默认方案

- Git：每个阶段使用独立 `stage/*` 分支保存可恢复版本，阶段通过后再合入 `main`。
- TypeScript 与严格类型检查：页面、API 和领域契约共享类型，降低数据结构漂移。
- 独立 Prompt 文件和版本号：全局提示词与阶段提示词不写入路由或页面组件。
- Mock 自动化测试：无模型 Key 时仍可离线验证状态、解析和错误路径。
- Web 端优先：PRD 的主要交付终端是桌面与移动浏览器。

## 3. 触发的按需模块

- 持久化数据库：事件、来源、引用、审核状态和订阅均需跨会话保留；采用平台 D1/SQLite 兼容存储。
- 异步任务状态：抓取和 AI 处理可能超出普通请求时限；后续阶段采用提交任务 + 查询状态。
- 模型服务适配层：由 AI 抽取与合并需求触发；离线回归保留确定性 mock，Stage 02 接入 DeepSeek Responses API，以 V4 Flash 为主模型、V4 Pro 为确定性门禁触发的升级模型。
- 浏览器测试：PRD 明确要求桌面、移动端和键盘可用性。

## 4. 偏离或暂缓的默认方案

- Python 3.11 + FastAPI：改为 Sites 的全栈 TypeScript/Next.js 兼容运行时。原因是当前网站可在同一部署单元内完成页面、API 与持久化，避免维护和部署第二套服务。若后续抓取、文档处理或离线评测明显更适合 Python，再新增独立 worker，而不是复制业务规则。
- Node.js 22 LTS：本机实际为 Node.js 24，项目脚手架与构建验证兼容，因此不为形式一致而降级；CI/托管运行时以项目锁文件和构建结果为准。
- 正式登录、邮件发送、定时抓取：暂缓到核心情报链路验证后，避免在 Agent 质量未成立前扩大范围。
- 真实模型：本地 Key 已配置且认证只读检查通过；Stage 02 必须完成 Flash 普通路径与 Pro 升级路径的真实冒烟，未完成前不算模型验收通过。

## 5. 强制底线检查

- 密钥与隐私：通过。真实 Key 仅由服务端环境变量读取，`.env` 不入库。
- 数据与任务可恢复：计划通过 D1 和显式状态枚举实现；第一阶段完成最小事件状态。
- 输入输出校验：通过 Zod/等价 Schema 在服务端校验，AI 输出再次验证。
- 错误与日志边界：统一错误结构，不向页面返回堆栈，不记录密钥与完整来源正文。
- 测试与真实模型验收：每阶段运行自动化测试；Stage 02 通过预览 API 完成 Flash 与 Pro 真实冒烟，不以 mock 替代；本阶段无界面改动，因此不重复进行视觉验收。

## 6. 需要产品经理决定的问题

无。模型供应商、自动发布阈值和邮件供应商在对应阶段用评测与成本证据再冻结。
